## API (all under the standard `ApiResponse` envelope; `Idempotency-Key` honoured on writes)

`/api/v1/production/sample-requests` — resource `production-sample-requests`

| Method / path | Permission | Who | Effect |
|---|---|---|---|
| `POST /` | CREATE | back office | DRAFT round 1, `SR-yyyyMMdd-nnnn`; body `customerId, designSnapshotId, blankSku, quantity (1..1000), dueDate?, quoteId?` (quoteId refused, see Gaps). Snapshot must be the customer's confirmed design for the blank's product. 201 |
| `GET /` | READ | back office, portal (own only) | page/size/sort (`createdAt,dueDate,requestNumber,status`), filters `status[]`, `customerId`, `designSnapshotId`, `search` (number) |
| `GET /{id}` | READ | same | round + `rounds[]` (whole chain, feedback kept) + `nextRoundId` + `productionOrder` ref + audit |
| `PUT /{id}` | UPDATE | back office | edit DRAFT specification |
| `POST /{id}/submission` | UPDATE | back office | `{warehouseId}`: re-verifies the design, checks blanks ATP in that warehouse, DRAFT→SUBMITTED + SAMPLE LSX (PENDING_PREPRESS, history row) in one transaction |
| `POST /{id}/sending` | UPDATE | back office | READY→SENT_TO_CUSTOMER, `sent_at` (off-system hand-over) |
| `POST /{id}/approval` | UPDATE | customer (portal) or Sales on behalf | SENT→APPROVED, `responded_at/by`, publishes `SampleApproved` in the same transaction |
| `POST /{id}/change-request` | UPDATE | same | `{feedback ≤2000}` SENT→CHANGES_REQUESTED |
| `POST /{id}/next-round` | CREATE | back office | after CHANGES_REQUESTED: new DRAFT round+1 (`previous_round_id`); optional body = new specification, empty = copy. Second call 409 `SAMPLE_NEXT_ROUND_EXISTS`. 201 |
| `POST /{id}/cancellation` | UPDATE | back office | `{reason ≤500}` DRAFT→CANCELLED |

`/api/v1/production/orders` — resource `production-orders`: `GET /` (filters `type[]`, `status[]`,
`warehouseId`, `dueFrom`, `dueTo`, `sampleRequestId`, `salesOrderId`, `search`; sort
`createdAt,dueDate,orderNumber,status`) and `GET /{id}` (quantities + status history). No create
endpoint: SAMPLE LSX come from submission, ORDER LSX from the release event.

Errors: `INVALID_SAMPLE_REQUEST_TRANSITION` 409, `SAMPLE_NEXT_ROUND_EXISTS` 409,
`PRODUCTION_SOURCE_CONFLICT` 409 (new, en/vi bundles); reused `DESIGN_SAMPLE_NOT_APPROVED`,
`CUSTOMER_NOT_FOUND`, `WAREHOUSE_NOT_FOUND`, `INSUFFICIENT_STOCK`, `VALIDATION_FAILED`, `FORBIDDEN`,
`OUT_OF_DATA_SCOPE`, `NOT_FOUND` (another customer's round answers 404).

Access: scope is enforced in the service, endpoints keep scope ALL (an OWN declaration would switch off
the WAREHOUSE restriction). Portal-only users are held to their own customer (`CustomerService.findByUserId`)
and refused back-office verbs; WAREHOUSE-scoped users (PRODUCTION/QC/WAREHOUSE staff) see LSX of their
warehouses and only the sample rounds made there.

## Release → ORDER production orders

`OrderReleaseListener` (`@ApplicationModuleListener`, async after commit, own transaction) calls
`OrderProductionService.createFor`: validates the event shape; reads the order through
`OrderService.findById` (must exist, released from that warehouse; a CANCELLED order gets none); every
line must match the order's line (sku, design, checksum, quantity); BR-PRD-08 from this module's rounds
(named sample must be APPROVED, same customer/design/blank; none named → latest approved of the pair,
else a COMPLETED ORDER LSX of the design for another order, else refused). All lines are decided before
any write; writes go in line-id order; any refusal rolls back the whole release and leaves the event
publication incomplete (logged). BR-PRD-01: `createIfAbsent` takes a transaction advisory lock on the
source, re-reads, inserts + first history row; the partial unique indexes stay the backstop. A replay
returns the existing LSX unchanged (status not reset) or fails `PRODUCTION_SOURCE_CONFLICT` if it
disagrees. Deposit/credit (BR-PRD-09) is trusted from order, not repeated.

## Gaps and decisions needed (not claimed done)

1. **CUSTOMER has no `production-sample-requests` grant** in `V20261010000500` (develop `1de8f42`).
   Today a portal customer gets 403 (pinned by HTTP test); Sales can record the answer on their behalf.
   Needed from the DB owner (Tu): grant `CUSTOMER → production-sample-requests: VIEW_PAGE, READ, UPDATE`
   and `UPDATE identity.app_role SET version = version + 1 WHERE code = 'CUSTOMER'`. The ownership rules
   for that case are already implemented and tested with a test-only grant.
2. **Quote link**: `quote_id` has no FK and no quote module exists until SCRUM-448, so a non-null
   `quoteId` is refused (`VALIDATION_FAILED`) rather than stored unverified.
3. **Workshop transitions** SUBMITTED→IN_PRODUCTION→READY exist on the aggregate
   (`startProduction`, `markReady`) but are triggered by the SAMPLE LSX workflow of SCRUM-396..401;
   tests set READY on the row as a stand-in. Producing `ProductionCompleted` is also that work.
4. **Recording an answer is UPDATE** (as granted to Sales). QC_STAFF also holds UPDATE on sample requests,
   so a QC user of the making warehouse could technically record an answer; restricting that needs a
   grant decision, not a role check in code.
5. **Customer eligibility (C02)** — whether BLOCKED/unactivated customers may get samples — is still
   undecided; only existence is checked.
6. **Blanks** at submit are an availability check (ATP ≥ quantity in the chosen warehouse), not a hold;
   issuing blanks to PRODUCTION is SCRUM-397.
7. `OrderCancelled` is not consumed by production yet (cancelling an LSX is BR-PRD-10 / later story).
   A release whose order is already CANCELLED when the listener runs creates nothing.
