## Baseline failure analysed (not caused here, not fixed here)

`GoodsReceiptIntegrationTest` (2–3 of 5) and sometimes
`SupplierProcurementIntegrationTest.fullReceiptIsFulfilmentAndCloseShortIsNot` fail with
`Invalid receipt/expiry date` from `inventory.enforce_sku_policy()`. Evidence, 2026-10-12:

- With a null expiry the only reachable branch is `NEW.received_at > clock_timestamp()`
  (V20261010000050); the receipt stamps `received_at` from the JVM clock and inserts ~15–20 ms later.
- A temporary probe (removed, not committed) in the **same Spring context and container** as
  `GoodsReceiptIntegrationTest` measured the database clock **58.6 ms behind** the JVM (RTT 1.5 ms):
  inserts with `received_at` 0/20/50 ms in the past were refused, 1 s in the past accepted. Other
  containers measured −7.7 ms and +75.6 ms within minutes: the Docker Desktop/WSL2 VM clock drifts
  against the Windows host.
- The same test fails identically on a clean detached checkout of develop `1de8f42`; the number of
  failing tests varies between runs (3, 3, 2); `SupplierProcurementIntegrationTest` passed on a rerun.
- Conclusion: environment clock skew meeting a zero-tolerance trigger. Options for the inventory
  owner: a small tolerance (`received_at > clock_timestamp() + interval '5 seconds'`), or syncing the
  WSL2 clock on the dev machine/CI runner. No trigger or test was changed in this lane.
