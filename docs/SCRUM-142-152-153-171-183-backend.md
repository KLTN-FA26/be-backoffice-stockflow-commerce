## SCRUM-152 — FEFO at allocation, reservation and allocation split

**Defect fixed.** `InventoryServiceImpl.reserve()` ran `StockAllocator.plan()` at checkout and put the order's hold
on stock items, so a bin and a lot were chosen before the order had a warehouse (docs 01 "Reserved" vs
"Allocated", 03 §6, 04c F-FUL step 02, BR-STK-006).

**Final rule.**

| Step | What happens | Where |
|---|---|---|
| Checkout | One **SKU reservation** per order line: `stock_reservation` row with `stock_item_id` NULL, quantity of a SKU, checkout deadline. ATP = unheld AVAILABLE unexpired `on_hand` − live SKU reservations, checked under the SKU advisory lock; the database re-checks a looser bound (`tg_stock_reservation_soft_atp_*`). | `InventoryService.reserve` |
| Payment / credit | pin / re-arm work on SKU reservations as before; allocations never expire. | `pinReservations`, `rearmReservations` |
| Expiry | the sweeper expires SKU reservations (SKIP LOCKED batches) and publishes `StockReservationReleased(RESERVATION_EXPIRED)`; the order cancels as before. | `ReservationSweeper` |
| Release to a warehouse | the order's SKU reservations become **allocations**: FEFO (earliest expiry, then earliest real `received_at`) over AVAILABLE, unexpired stock on **pickable, usable** locations of that warehouse only; one `stock_reservation` row per bin/lot with `allocated_from_id`, `expires_at` NULL; the SKU reservation turns `ALLOCATED`; the order line swaps the reservation id for the allocation ids. All or nothing: `INSUFFICIENT_STOCK` refuses the release, and so does `RESERVATION_NOT_ACTIVE` when one line's reservation expired or was released first (the sweeper or a manual release won the race) - the other lines are not sent to the warehouse alone. | `OrderReleaseService.release` → `OrderStockAllocation` → `InventoryService.allocate` |
| Stock-only order picked from CONFIRMED (Sprint 2 path kept) | task creation picks the single warehouse that can allocate every line, that the caller may work in and that the assignee belongs to; several → 409 "release it first"; none → 409 `INSUFFICIENT_STOCK`. Allocation happens in `OrderService.releaseToFulfillment(orderId, warehouseId)`. | `FulfillmentServiceImpl.createTask` |
| Pick | one pick line per allocation (bin + lot from the allocation); confirmation consumes that allocation exactly once (`uk_pick_line_reservation_live`, `uk_stock_movement_pick_line`, unchanged). | `PickListService.confirm` |
| Cancel | before allocation: the SKU reservation is released; after: the allocations (picked goods go through put-back as before). | `OrderServiceImpl.cancelLoaded` |
| Short pick (X-SHORT) | `POST /api/v1/fulfillment/tasks/{id}/pick-lines/{lineId}/short` → line SHORT (`short_qty`), order ON_HOLD `INVENTORY_ISSUE`, no ledger row. `POST …/reallocation` (coordinator / warehouse manager) → the short allocation is released (`SHORT_PICKED`) and the quantity allocated again FEFO on other pickable bins of the same warehouse, never the short bin; the short line becomes CANCELLED (shortfall kept), new lines are added; when no line is SHORT the order resumes. The short report also opens a blind `SHORT_PICK` cycle count of that bin, SKU and lot (one open recount per bin, SKU and lot; X-SHORT step 03). | `PickListService.reportShort/reallocateShort`, `InventoryService.reallocate` |

Other writers of free stock respect SKU reservations: production holds (`reserveForProduction`) and transfer
dispatch take the SKU lock and refuse to go below the SKU reservations. Reality-driven reductions (QC, adjustments,
expiry) are not refused; a release then reports the shortage.

Lock order everywhere: SKU advisory locks (sorted) → SKU reservation rows → stock rows by id. `prepareReservation`
now takes SKU locks only (checkout no longer touches stock rows).

**Schema.** `V20261019000800__inventory_sku_reservation_and_allocation.sql`: `stock_reservation.stock_item_id`
nullable, `sku` (backfilled, NOT NULL, FK), `allocated_from_id` (FK), status `ALLOCATED`, checks
`ck_stock_reservation_kind` / `ck_stock_reservation_allocation`, trigger `tg_stock_reservation_sku`, the ATP safety
net, two partial indexes. No data is reset; legacy rows only gain `sku`.

**Legacy live orders.** Checkout holds placed before this version stay on their stock items and stay pickable;
releasing such an order allocates nothing. Production, print and subcontractor holds are unchanged rows.

**Events.** Each allocation (release, reallocation) publishes `contracts.StockAllocated` (order, allocation id, SKU,
bin, lot, quantity); available-to-promise does not change. Nobody listens yet.

**API compatibility.** Same endpoints and records. `StockReservation.stockItemId/locationCode/lotNumber` and
`OrderHold.locationCode` are null for a SKU reservation; `HoldView.Status` gained `ALLOCATED`;
`GET /inventory/reservations` lists SKU reservations with a null location (not visible to warehouse-bound users);
`PickLineResponse` gained `shortQty`. Per-warehouse ATP / `StockLevel.atp` is capped at the system-wide ATP.

## SCRUM-142 — batch / lot identity

`V20261019000900__inventory_stock_lot_traceability.sql`: `inventory.stock_lot`, one row per goods receipt and
(SKU, lot number, expiry) with a snapshot of receipt / PO / supplier; `stock_item.lot_id`, `stock_movement.lot_id`,
`stock_movement.order_id`, and an `order_number` snapshot on `stock_movement` and `stock_reservation` (filled by
`tg_*_order_number` from `ordering.customer_order`; a SKU reservation, written before its order row, has none).
`inventory.item_in_use` counts `stock_reservation` and `stock_lot`, so the SKU rename guard answers before a
foreign key does. A reused lot number on another receipt is another lot. Receipts open lots
(`ReceiveStockCommand.origin`, passed by procurement); moves, putaway, holds and put-backs carry the lot (a
put-back, a production hand-over and a return of unprinted blanks merge only into a layer of the same lot and
expiry, `StockItem.isSameGoodsAs`: one receipt may bring a lot number twice with two expiries); every
ledger line the application writes names its lot. Triggers resolve the lot for rows written without one (UNTRACED
lot when no receipt is known). Existing data is backfilled (receipt lots from the ledger, UNTRACED for the rest,
ledger lot/order where unambiguous) with the append-only guard lifted for those statements only.

## SCRUM-153 — lot traceability report

`inventory-stock-movements:READ`, data scope WAREHOUSE:

- `GET /api/v1/inventory/lots?sku&lotNumber&warehouseId&from&to&page&size` — lots, newest receipt first, with
  origin and current balance (on hand / available / held) in the warehouses asked about.
- `GET /api/v1/inventory/lots/{lotId}?warehouseId` — origin, balances by location, allocations and holds
  (with `allocatedFrom` and `orderNumber`), customer orders it left for (`orderNumber`, picked / put back).
- `GET /api/v1/inventory/lots/{lotId}/movements?warehouseId&from&to&page&size` — ledger lines oldest first.

Dates are business days (Asia/Ho_Chi_Minh), inclusive. A warehouse-bound caller is narrowed to their warehouses;
naming another warehouse is `OUT_OF_DATA_SCOPE`, a lot never held there is `NOT_FOUND`. Orders carry their id and
the number snapshot taken when the units moved; customer names are not in the report (inventory does not read
`customer`). `available` = on hand − held of AVAILABLE rows not past expiry.

## Cycle counts (X-SHORT step 03)

- A short report calls `PickConsumption.requestRecount`: a blind `SHORT_PICK` count, number `CC-yyyyMMdd-nnnn`
  from `platform.document_sequence`, PLANNED for today, one line (bin, SKU, lot, book on-hand). An advisory lock
  on the bin, SKU and lot keeps two concurrent short reports from opening two counts.
- `GET /api/v1/inventory/cycle-counts?status&warehouseId&page&size` (`inventory-cycle-counts:READ`): a counter sees
  neither the expected quantity nor the note (which says what the picker found); a warehouse manager sees both.
  `V20261019001000` grants VIEW_PAGE and READ to WAREHOUSE_STAFF, who count (docs 04c F-CNT); before it only the
  manager and the planner held the resource.
- **The short bin is frozen while its recount is open** (decision 2026-10-19): the free units of an AVAILABLE,
  unexpired layer in a bin, SKU and lot with an open SHORT_PICK count are left out of every available-to-promise
  figure, the per-bin availability and the FEFO planner (`Recounts.frozen`). Its held units stay held. Otherwise the
  units the picker did not find would be sold and allocated again until somebody counts. The database's soft-ATP
  trigger is not changed: it stays the looser bound.
- `POST /api/v1/inventory/cycle-counts/{id}/cancellation` `{reason}` (`inventory-cycle-counts:APPROVE`, warehouse
  manager): the count turns CANCELLED, the reason is appended to the note, the freeze lifts. Again on a cancelled
  count: no-op; on a COMPLETED one: 409 `CYCLE_COUNT_NOT_OPEN`.
- A reallocation locks the pick, then the order, then stock rows, the same order as a short report; a cancellation
  locks the order before the stock rows, so taking the order last could deadlock against it.
- Counting and posting the difference remain the cycle-count story's (not in this sprint).

## SCRUM-183 / 171 — category hierarchy and navigation

- `PUT /api/v1/categories/{id}/parent` `{"parentId": uuid|null}` (`products:UPDATE`): moves a category and its
  whole subtree, rewrites `path`/`depth` parents first, keeps codes, slugs and product assignments; refuses moves
  under itself or its subtree and past depth 10 (`VALIDATION_FAILED`, field `parentId`); the tree advisory lock
  serialises moves and creations, so crossing moves cannot make a cycle.
- `product :: api` `CategoryNavigation` reads `product.categories` (no second category store).
- `GET /api/v1/catalog/categories` — the visible tree, nested (an inactive category hides its subtree).
- `GET /api/v1/catalog/products?category={slug}` — the listing inside that category and its subcategories,
  filtered in SQL; unknown/hidden slug → `CATEGORY_NOT_FOUND`.

### Final review, 2026-10-19 (after merging develop `535e6c38`)

Three independent reviews of the diff against develop (reservation/allocation; lots, trace and migrations; short
pick, recounts and categories) against docs 01/03/04c/05. Fixed: the migration version clash with develop
(renumbered `000800`/`000900`); a deadlock between reallocation and cancellation (lock order); warehouse staff
without access to the counts they make (`V20261019001000`); the picker's found count visible on a blind count; two

reservations stay covered (a physical correction is not refused; an over-promise then surfaces at release as
`INSUFFICIENT_STOCK`); the lot trace's `available` does not subtract a frozen layer.
