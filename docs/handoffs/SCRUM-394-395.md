## Implemented and verified without persistence

| Acceptance | Foundation behavior |
|---|---|
| Sample request lifecycle | Draft -> Submitted -> In Production -> Ready -> Sent to Customer -> Approved / Changes Requested; only Draft can cancel; only Changes Requested can reopen Draft. |
| Customer feedback and rounds | Nonblank change feedback, actor/time and the exact reviewed specification are retained. Reopening increments the round once. Stale version/round and stale production callbacks are rejected. |
| Approval lock | Submitted specifications cannot be edited. Approved is terminal. Immutable review captures snapshot ID, SHA-256 checksum and blank SKU, quantity and due date. Rehydration validates the history and emits no event. |
| `SampleApproved` | Aggregate records the existing `contracts.SampleApproved`; service saves before publishing the payload. Repeated/stale approval cannot publish another event. Actual durable delivery awaits persistence/wiring. |
| SAMPLE creation | First-round submit verifies warehouse and frozen design, obtains one SAMPLE production order by source, then saves the request in the same declared application transaction. Stale submit is a conflict and creates nothing. |
| ORDER creation | `OrderProductionService.receive` accepts the existing `OrderLinesReleasedForProduction`, validates every line and reference before any insert, and creates PENDING_PREPRESS orders by order-line source. |
| New/repeat designs | Explicit approval must match customer + design snapshot + checksum + blank. A null approval ID for a repeat design resolves an existing approval for that customer/design/blank; it never bypasses the sample gate. Quantity/due date may differ from the physical sample. |
| Duplicate/replay | Source identity is independent of event delivery. Existing payload must match; changed customer/order/warehouse/specification/approval conflicts. Atomic insert-or-get must return the persisted winner. Replay preserves completed workflow state and does not reread artifact bytes. |
| Batch/race contract | Entire batch is validated before writes; insert claims are ordered by source ID. A conflicting concurrent winner is rejected. Database atomicity/races are explicitly not proven by these mock-based tests. |
| Access control | Shared server-side `PermissionChecker` is used. Anonymous/permission failures precede loading. Customer identity is resolved through `customer::api`; even a CUSTOMER with ALL scope cannot access another customer's sample or edit drafts. Staff OWN is limited to creator; nested scope cannot widen access. |
| Module boundary | New `production` module only imports `customer::api`, `design::api`, shared common/contracts. No order, inventory, fulfillment or identity internals are imported. |

## Open business decision: subsequent sample production rounds

The allocation requires both multiple rounds and exactly one LSX per sample request. It does not
say whether a new round creates another LSX or reopens the previous one. A clarification was sent
to the user and remains unanswered at this milestone:

1. One LSX per `(sample_request_id, round)`; or
2. One LSX per request, with reopening and immutable round execution history.

The aggregate supports feedback/revision and preserves prior rounds. **The service refuses submit
for round > 1 until this decision is made**. This guard is a temporary blocked capability, not an
approved business rule. Its test documents that no duplicate or reused completed LSX is invented.
Do not approve a sample source uniqueness migration until this point is resolved with the owner.

## Required persistence mapping for Tu and integration follow-up

These are required logical fields/invariants, **not an invented physical schema or migration**.
Align final table/column names with SCRUM-422 before writing JPA mappings.

| Record | Required fields and constraints |
|---|---|
| Sample request | UUID `id`; `customer_id` FK; optional `quote_id` FK with same customer; creator/audit fields; `status`; positive `round`; nonnegative CAS `version`; `design_snapshot_id` FK; 64-char lowercase SHA-256 `design_checksum`; `blank_sku` FK; positive `quantity`; nullable `due_date`; selected `warehouse_id` FK for submitted/active/reviewed round. |
| Round review | `sample_request_id`, positive `round`, immutable specification fields, `decision`, feedback, actor FK, timestamp. Unique `(sample_request_id, round)`; nonblank feedback for CHANGES_REQUESTED; prior rounds ordered and all changes-requested; approval only for the current final round. Approved specification cannot diverge from its review. |
| Production order | UUID `id`; document number from `platform.document_sequence` when introduced; `type`, workflow `status`, customer and warehouse FKs; concrete sample-request or order-line source FK; order ID/number for ORDER; immutable specification; resolved approved-sample reference for ORDER; audit/version fields. Source type must match the nullable FK combination. |
| Source uniqueness | Unique ORDER `order_line_id`, including completed/cancelled records (never free the source on soft deletion). SAMPLE uniqueness awaits the round decision above. Cross-schema FKs should use actual concrete source columns, not an unconstrained polymorphic UUID. |
| Atomicity | `findByIdForUpdate` must lock and refresh aggregate/history. `save` must CAS the supplied prior version and flush before event publication. Domain version advances once per mutation; adapter must avoid double increment with JPA `@Version`. `insertOrGet` must use database uniqueness with a safe winner read, not just find-then-insert or swallowing a constraint error in an aborted transaction. All release lines and all sample submit writes commit/roll back together. |
| Approval durability | Persist immutable approval and publish existing `SampleApproved` in the same transaction through Spring Modulith's registry. Rollback must leave neither approval nor event publication. |
| Authorization | Seed `sample-requests` READ/CREATE/UPDATE/APPROVE with role/scope mappings from the approved plan, `production-orders` permissions and production staff role. Increase affected `app_role.version` with grant changes. Add controller `@PermissionResource`/method guards, shared envelope/validation/idempotency and auditable transitions when runtime wiring is enabled. |

Required order adapter: resolve authoritative customer and validate release warehouse through
order's public API. The release publisher must enforce customer-line/design ownership, approved
sample requirement and payment/deposit conditions before publishing. Production cannot infer
customer from the current event because its unchanged contract has no customer field.
