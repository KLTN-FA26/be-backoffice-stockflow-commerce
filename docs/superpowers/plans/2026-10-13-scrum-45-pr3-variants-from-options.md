# SCRUM-45 PR 3 — Variants from options, SKU rules and matrix generation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Variants are built from a product's axis options: the attribute signature is derived, the SKU is
generated by rule or typed by hand and validated once, and a whole matrix can be generated in one call
(GitHub #95, Jira SCRUM-60, SCRUM-61; the FE matrix screen SCRUM-373 consumes it).

**Architecture:** Three pure domain units — `VariantSignature`, `SkuCodeRule`, `VariantMatrix` — plus the
shared-kernel `Sku` aligned with `ck_variants_sku`. `ProductVariantService` (still not an aggregate, as its
javadoc explains) resolves option value ids through the product's `ProductAttributeSet` (PR 2), writes
`product.variant_attribute_values`, and keeps locking the product row first. The default variant takes
the first combination and keeps its SKU (spec D1). The variant endpoints move to `product-variants`.

**Tech Stack:** Java 21, Spring Boot 3.5, Spring Data JPA / Hibernate, PostgreSQL 16 (Testcontainers),
JUnit 5, AssertJ, MockMvc.

**Spec:** `docs/superpowers/specs/2026-10-13-scrum-45-variant-sku-design.md` — §4 D1, D3–D8, §5, §6
"Variants" and the option-order paragraph of §6 "Product attributes". Builds on PR 2 (#100, branch
`feature/SCRUM-45-product-axes`).

## Global Constraints

- **No migration.** `product.variants`, `product.variant_attribute_values` and their triggers exist (`V20260928001100`, `V20260928001300` §5, `V20261008000200`).
- Work in the worktree `.worktrees/scrum-45-pr3` on branch `feature/SCRUM-45-variants-from-options` (stacked on PR 2).
- **Speed rules (owner, 2026-10-13):** during Tasks 1–2 run only the focused tests named in each task plus `ModularityTest`, `ArchitectureTest` and `python -X utf8 tools/verify.py`. Run the full `mvn verify` **once**, in Task 3.
- **SKU alphabet (D6):** `com.stockflow.common.domain.Sku` becomes exactly `ck_variants_sku`: strip, upper-case with `Locale.ROOT`, then `^[A-Z0-9][A-Z0-9._-]{0,63}$`. The current pattern `[A-Z0-9\-]{3,64}` rejects SKUs the database holds (a product code with `_`, a 1–2 character code). This widens what is accepted and refuses a leading `-`, which the database already refuses. `ProductVariantService.SKU` and `normalise` go away in favour of `Sku`.
- **Signature (D4):** `ATTR=VALUE;ATTR=VALUE`, attribute codes ascending, value codes from the dictionary. Special forms: `DEFAULT` (the default variant of a product with no axes), `SKU=<sku>` (an extra variant of a product with no axes). The client never sends a signature.
- **SKU rule (D5):** `PRODUCT_CODE-VALUE_CODE-VALUE_CODE…`, value codes in **axis order** (`product_attributes.sort_order`, then attribute code). A collision gives `409 VARIANT_SKU_ALREADY_EXISTS`; a result over 64 characters gives `400 VALIDATION_FAILED` ("supply a SKU by hand"). There is no automatic suffix.
- **Order (spec §6):** axes by `sort_order` then attribute code; options by dictionary `attribute_values.sort_order` then value code. The matrix is enumerated in that order: the first axis varies slowest. Its first combination is "the first combination" of D1.
- **D1, default transform:** on a product with axes, the first combination that any create path (`add` or `generation`) produces goes to the default variant, provided that variant still has signature `DEFAULT`. The variant gets that combination's options and signature, its **SKU is kept**, and its name becomes the generated name unless a name was sent. No row is inserted for that combination.
- **Ruling (closes the PR 2 review's open point):** while any variant of the product carries an option, an axis can no longer be **added**. The request gets `409 PRODUCT_AXES_LOCKED` ("variants already use the current axes"). Removing one was already refused, because its options are in use. Adding options stays allowed. The rule lives in `ProductAttributeSet.replaceAxes`, decided by `!valueIdsUsedByVariants.isEmpty()`.
- **Create paths:**
  - On a product **with axes**, each axis gets exactly one option value, and the value must be an option of that axis on this product. A missing axis, two values on one axis, or a value that is not an option of the product gives `400 VARIANT_OPTIONS_INVALID`. `sku` is optional (D5 when absent); `name` is optional (`"<product name> – <label> / <label>"`, labels in axis order).
  - On a product **without axes**, options must be empty and `sku` is required (otherwise `400 VALIDATION_FAILED`). The signature is `SKU=<sku>`.
  - A combination that already exists on the product gives `409 VARIANT_SKU_ALREADY_EXISTS`, the existing code and message.
- **Update:** the options of a variant may change only while the variant is `DRAFT` (`409 INVALID_VARIANT_TRANSITION`). Its signature is re-derived and its SKU is **not** regenerated. The existing rule that the SKU may change only in DRAFT stays.
- **Generation (D7):**
  - `optionValueIds` (map attributeId → value ids) is optional and restricts the matrix; when omitted, every option of every axis is used.
  - Combinations whose signature already exists on the product are skipped.
  - At most **100** variants are created per call; beyond that the request gets `400 VARIANT_MATRIX_TOO_LARGE`, counted after skipping.
  - The response is `{created: [VariantResponse], skipped: n}`.
  - A product with no axes gets `400 VARIANT_OPTIONS_INVALID`.
  - It is idempotent.
- **New error codes**, in `ErrorCode` and both bundles:
  - `VARIANT_OPTIONS_INVALID("The options do not name one value per axis of this product", 400)`, VI: "Mỗi trục của sản phẩm phải có đúng một giá trị".
  - `VARIANT_MATRIX_TOO_LARGE("Too many variants for one generation", 400)`, VI: "Số biến thể cần sinh vượt quá giới hạn một lần".
- **Permissions (D8):** every variant endpoint moves from `product-products` to `product-variants`. Read endpoints use READ. `add` and `generation` use **CREATE**. `update` and `blocking` use UPDATE. `activation` and `obsoletion` use APPROVE. The resource is already declared on `ProductAttributeController`; do not declare it again. The seeded roles give nobody less access (checked: ECOMMERCE_ADMIN has all; SALES_STAFF has VIEW_PAGE, READ, CREATE, UPDATE).
- Audit: `resourceType = "product-variant"`, as today. Generation is audited as `CREATE` on `#productId`.
- Same house rules as PR 1 and PR 2: `Identifiers.newId()`, public proxied and handler methods, javadoc says why (and is updated where the old reason no longer holds), English in code, commits per `.claude/skills/git-commits/SKILL.md` with no attribution trailers.

## Review Focus

1. **A product code with `_` or `.`** (`CUP_PET`, `LID.80`). The default variant must flow through inventory and catalog calls that build `new Sku(...)`; today that throws. Pinned in Task 1 (`theSkuAlphabetIsTheDatabases`) and Task 2 (`aProductCodeWithUnderscoreWorksEndToEnd`).
2. **Generation called twice, or after a manual add of one combination**: the second call creates nothing and counts it as skipped. Pinned in Task 2 (`generationIsIdempotent`).
3. **The first generation on a product whose default variant is still `DEFAULT`**: the default takes the first combination, keeps its SKU, and no extra row appears. N combinations give N variants in total, not N+1. Pinned in Task 2 (`theDefaultVariantTakesTheFirstCombination`).
4. **Listing variants with their options**: no query per variant. Pinned in Task 2 (`listingVariantsIsConstantInQueries`).
5. **Adding a third axis after variants exist** gets 409, not variants that silently have no value on the new axis. Pinned in Task 1 (`noAxisCanBeAddedOnceVariantsUseOptions`) and Task 2 (`addingAnAxisAfterGenerationIsLocked`).

**Interfaces:**
- Produces:
  - `record Sku(String code)`, same name and package: compact ctor normalises (strip, `toUpperCase(Locale.ROOT)`) and validates `[A-Z0-9][A-Z0-9._-]{0,63}`; `IllegalArgumentException` as today, so `SkuValidator`/`@ValidSku` keep working. Javadoc names `ck_variants_sku` as the single source.
  - `record VariantSignature(String value)`:
    - `static VariantSignature of(Map<String, String> attributeCodeToValueCode)`: sorted by attribute code, joined `A=V;B=W`, ≤ 512.
    - `static VariantSignature defaultSignature()`: `DEFAULT`.
    - `static VariantSignature ofSku(Sku sku)`: `SKU=<code>`.
    - `boolean isDefault()`.
  - `final class SkuCodeRule { static Sku generate(String productCode, List<String> valueCodesInAxisOrder) }`: throws `BusinessException(VALIDATION_FAILED)` when the result exceeds 64 characters.
  - `record Combination(List<AxisOption> options)`, nested in `VariantMatrix` or top level, plus `final class VariantMatrix { static final int MAX_PER_CALL = 100; static List<Combination> of(List<List<AxisOption>> optionsPerAxisInOrder) }`. Enumerated with the first axis varying slowest. A helper `List<Combination> missing(List<Combination> all, Set<VariantSignature> existing, Function<Combination, VariantSignature> sign)` throws `VARIANT_MATRIX_TOO_LARGE` when more than `MAX_PER_CALL` remain.
  - `ProductAttributeSet.replaceAxes`: adding an axis while `valueIdsUsedByVariants` is non-empty gives `PRODUCT_AXES_LOCKED`.
  - `ProductAttributeSet.optionFor(UUID attributeId, UUID valueId)` returns `Optional<AxisOption>`.
  - `ErrorCode.VARIANT_OPTIONS_INVALID`, `VARIANT_MATRIX_TOO_LARGE` plus their bundle lines.
